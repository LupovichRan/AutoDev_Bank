Scope note: research was done on 2026-11-04. Items older than 2025 are marked "[older]". Paid or source-available (non-OSI) tooling is marked "[PAID]" or "[SOURCE-AVAILABLE]". Where only secondary sources (vendor blogs, job boards) were found, that is said explicitly. ## Key Question 1: Can a PWA alone meet banking needs in 2026? What do app stores and regulators require that a PWA cannot satisfy?

### Takeaway
On iOS 26 a Home Screen web app gets web push (incl. declarative push), badging, WebAuthn/passkeys, camera, Digital Credentials and OPFS storage, so the day-to-day banking UI is feasible as a PWA. What a PWA cannot do on iOS: Web NFC, Web Bluetooth, background/periodic sync, app shortcuts, share-target, and, critically for a regulated bank, hardware device attestation (App Attest / Play Integrity), hardware-bound keys with a verifiable binding story, screenshot blocking, and App Store presence. Those last four are what push every real bank to ship a native shell.

### Cited Findings
- iOS 26: "every website added to the Home Screen opens as a web app" by default; users can toggle "Open as Web App" off; "there are now zero requirements for 'installability' in Safari"; manifest still used for icons/benefits — [WebKit: WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- Safari 26.0 adds the WebAuthn Signal API (`PublicKeyCredential.signal`), the W3C Digital Credentials API (`navigator.credentials.get()` with `"org-iso-mdoc"`, user-gesture required, "not yet supported in WKWebView"), and File System WritableStream for OPFS — [WebKit: Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- firt.dev iOS Home Screen web app compatibility table (updated 13 Oct 2026): Web Push supported since 16.4 (installed web apps only; not in Safari tabs); Declarative Web Push since 18.4 (no service worker needed); App Badging since 16.4; WebAuthn since 14.5; Digital Credentials since 26.0; Camera getUserMedia since 13.0 ("Advanced Camera Controls" unsupported); OPFS since 15.2 with writable streams since 26.0; Web NFC unsupported; Web Bluetooth unsupported; Background Sync unsupported; Periodic Background Sync unsupported; `share_target` unsupported; manifest `shortcuts` unsupported on iOS (macOS only since 17.4); manifest `orientation` unsupported — [firt.dev iOS PWA Compatibility](https://firt.dev/notes/pwa-ios/)
- Declarative Web Push "allows developers to request a subscription and display notifications without an installed service worker", shipped in iOS/iPadOS 18.4 for Home Screen web apps — [WebKit: Meet Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/); [WebKit Features in Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)
- Permission prompts (push etc.) on iOS only work after the user adds the site to the Home Screen and opens it from there; some developers report iOS web push "may work initially but then stop unexpectedly" (secondary, unverified) — [OneSignal: Safari web push for iOS](https://documentation.onesignal.com/docs/safari-web-push-for-ios); [mobiloud 2026 guide](https://www.mobiloud.com/blog/progressive-web-apps-ios/)
- One secondary source claims Safari 27 (Sept 2026) added "no new features for Home Screen web apps" (not verified against WebKit) — [wavxsolutions](https://www.wavxsolutions.in/blog/pwa-on-ios-what-works)
- Apple App Store Guideline 4.2: "Your app should include features, content, and UI that elevate it beyond a repackaged website. If your app is not particularly useful, unique, or 'app-like,' it doesn't belong on the App Store." 2.5.6: "Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript." 2.5.2 forbids downloading/executing code that changes features (web content in a WebView is the accepted exception in practice; 4.7 explicitly permits "HTML5 and JavaScript mini apps"). The guidelines never mention "Progressive Web App" — [Apple App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Apple 3.2.1(viii): "Apps used for financial trading, investing, or money management should be submitted by the financial institution performing such services and must have necessary licensing and permissions in the locations where you make them available." 5.1.1(ix): banking/financial apps "should be submitted by a legal entity that provides the services, and not by an individual developer." 5.1.1(v): account deletion must be offered in-app if account creation is supported — [Apple App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Secondary sources (wrapper vendors) say Apple does not ban WebView apps but rejects "repackaged website" apps under 4.2; the "PWA wrapper" pattern is a well-known 4.2 rejection path; fixes are native navigation, push, offline, device integrations — [mobiloud](https://www.mobiloud.com/blog/app-store-review-guidelines-webview-wrapper/); [median.co](https://median.co/blog/will-apple-approve-my-webview-app)
- Google Play Financial Services policy: any app with financial features must complete the Financial features declaration in Play Console and comply with local regulation in every targeted region; personal-loan apps face extra disclosure rules; the July 15, 2026 policy update reframed Earned Wage Access and added user-data rules for third-party AI integrations; target-API-level deadline was Aug 31, 2026 — [Google Play Financial Services policy](https://support.google.com/googleplay/android-developer/answer/9876821?hl=en); [Play policy announcement July 15, 2026](https://support.google.com/googleplay/android-developer/answer/17134731?hl=en)
- Play Integrity API: verdicts `accountDetails` (installed via Play), `appIntegrity` (`PLAY_RECOGNIZED` = unmodified binary Play recognizes), `deviceIntegrity` with tiers `MEETS_STRONG_INTEGRITY` (Android 13+, hardware-backed + recent security patch), `MEETS_DEVICE_INTEGRITY`, `MEETS_BASIC_INTEGRITY`; opt-in `appAccessRiskVerdict` (screen-capture/overlay/accessibility-abuse apps), `playProtectVerdict`, `recentDeviceActivity`, `deviceRecall` (beta); default quota 10,000 requests/day (can be raised); standard requests use `requestHash` content binding, classic requests use `nonce`; Google says "Avoid caching integrity verdicts" and recommends tiered enforcement — [Android Developers: Play Integrity API overview](https://developer.android.com/google/play/integrity/overview)
- Play Integrity fully replaced SafetyNet on Jan 31, 2025 (secondary) — [trysonar blog](https://trysonar.app/blog/play-integrity-api-when-to-enforce-when-to-skip)
- EBA Opinion on SCA elements (EBA-Op-2019-06) [older, still governing]: a mobile app, browser, or key pair counts as a possession element only if a device-binding process creates a unique link between the app/key and the device; an app installed without such binding does not qualify — [EBA Q&A 2019_4827](https://www.eba.europa.eu/single-rule-book-qa/qna/view/publicId/2019_4827); [Norton Rose Fulbright summary](https://www.nortonrosefulbright.com/en/knowledge/publications/bf11898a/eba-delivers-opinion-clarifying-key-elements-of-strong-customer-authentication-sca-under-psd2); [Ravelin analysis](https://www.ravelin.com/blog/analyzing-the-eba-opinion-on-sca-elements)
- The EBA has not published an explicit opinion on WebAuthn/passkeys; vendor blogs argue a WebAuthn assertion with user verification can supply possession + inherence/knowledge, but a plain passkey login does not satisfy dynamic linking for payments because the challenge carries no transaction data; synced (iCloud/Google) passkeys weaken the "unique device link" argument — [Security Boulevard: Passkeys and PSD2 SCA dynamic linking](https://securityboulevard.com/2026/07/passkeys-and-psd2-sca-dynamic-linking-with-webauthn/); [Corbado: biometrics & payer awareness](https://www.corbado.com/blog/biometrics-payer-awareness); [247 CyberLabs: SCA and device binding](https://247cyberlabs.com/articles/understanding-strong-customer-authentication-sca-and-device-binding-under-psd2/)

### Inferences
- A PWA alone can deliver login with passkeys, push, camera-based ID capture (still frames via getUserMedia; no document-scanning hardware controls), and offline read-only state. It cannot deliver: NFC (tap-to-pay or NFC-chip passport/eID read), hardware attestation, verifiable device binding (synced passkeys are explicitly "roamed", so the EBA "unique link to device" argument is weak), screenshot blocking, true background sync, or App Store / Play Store listing. A regulated EU bank will almost certainly need a native shell for the SCA possession element and for Play Integrity / App Attest-backed fraud controls; the web front end can still be the primary UI.
- A "web-first" architecture is therefore viable only as "web core + thin native shell for attestation/keys/NFC/push", not "PWA only", unless the bank is willing to use SMS/OTP or a separate authenticator app as the possession element (which the EBA opinion also treats as weaker).
- Apple's 4.2 risk is real for thin wrappers; adding native biometrics/App Attest/push/offline-cache in the shell is exactly what makes the wrapper "app-like" and is also what the bank needs anyway.

### Gaps
- No primary Apple statement found on whether passkeys/Face ID work inside Home Screen web apps specifically (firt.dev lists WebAuthn supported since 14.5 but does not single out passkeys); needs a hands-on test.
- The reported "7-day storage eviction" for Safari was not covered in the fetched sources; firt.dev lists Persistent Storage (15.2) and Quota (17) but not eviction rules.
- The EBA/PSD3-PSR status in late 2026 could not be searched (budget exhausted). The 2019 EBA opinion is the governing text found; whether PSR (Payment Services Regulation) has been adopted and whether it changes device-binding language is unverified.
- Apple's App Attest documentation page returned only a title, so limits (keys per app, rate limits) and exact OS requirements are unsourced; the Flutter plugin summary in [pub.dev app_attest](https://pub.dev/packages/app_attest) says the backend must verify "certificate chain, challenge, app/team identifier, sign count, and assertion signature."

## Key Question 2: If a native wrapper is needed, which is the thinnest viable option around a web core? Capacitor vs Tauri 2 mobile vs Expo with WebView vs Kotlin Multiplatform

### Takeaway
Capacitor is the thinnest, most mature OSS "web core in a native shell" option, with MIT/Apache community plugins for biometrics, secure storage, SSL pinning and App Attest-style integrity. Tauri 2 mobile is stable since Oct 2024 and actively patched through 2.12.0 (Sept 2026) but has no supported native-UI embedding, thinner plugin coverage, and relies on the system WebView. Expo's `@expo/dom-webview` (SDK 56) makes "RN shell + web screens" plausible but brings the full RN/Hermes runtime. KMP is not a web wrapper at all; it is the choice if the team prefers shared Kotlin logic with native UI.

### Inferences
- For "web core + thin shell", Capacitor has the fewest moving parts: one WKWebView/Android WebView, a JS bridge, and small single-purpose plugins that map directly to Keychain/Keystore, LocalAuthentication/BiometricPrompt, URLSession/OkHttp pinning. Everything needed is MIT/Apache community-maintained; the paid Ionic enterprise layer is avoidable.
- Tauri 2 mobile is the KISS-est from a Rust/security purist view (no JS runtime, Rust command layer), but the ecosystem for banking-specific plugins (biometric, App Attest, pinning, secure storage) is thinner and there is no native-view embedding; treat it as a credible 2027 candidate, not the default for a regulated launch in late 2026.
- Expo DOM components make it possible to mix web screens into an RN shell, but you then carry Hermes + RN (~16 MB Android download, 230 MB RSS on Android in the SM benchmark) for a shell whose job is small. That contradicts KISS unless the team already wants RN for most screens.
- KMP is the right answer if the organisation prefers native UI per platform with shared Kotlin domain logic (Monzo-style); it is not a way to reuse the web client.

## Key Question 3: Which web framework (or no framework) best fits KISS: Lit/web components, Svelte 5, SolidJS, Preact, React 19, HTMX + server render, Vue?

### Takeaway
For runtime weight, Svelte 5, Solid, Preact and Lit all land in the 3–8 kB gzipped class versus ~42–58 kB for React+ReactDOM; Solid has the highest State of JS satisfaction five years running; React remains the hiring default and the backbone of most accessible component kits (Radix/shadcn). Rigorous apples-to-apples 2025/2026 size numbers do not exist in one place; the only multi-framework measurement found is a 2024 repo.

### Cited Findings
- State of JS 2025 (11,952 respondents on front-end frameworks): Solid "may only be used by 10% of respondents" but has "the highest satisfaction for five years running"; only Solid and Preact gained interest year-over-year; Alpine.js and HTMX swapped usage rankings; React tops pain-point mentions; average respondent has used 2.6 front-end frameworks — [State of JS 2025: Front-end Frameworks](https://2025.stateofjs.com/en-US/libraries/front-end-frameworks/)
- Secondary summaries of State of JS 2025: Svelte 5's Runes drew strong positive attention; a "91% retention" figure for Svelte 5 is reported by a blog but could not be confirmed on the official site — [Strapi takeaways](https://strapi.io/blog/state-of-javascript-2025-key-takeaways); [Medium "vibe shift"](https://hmnshudhmn24.medium.com/state-of-js-2025-is-out-the-vibe-shift-is-real-94841a161997)
- 2024 multi-framework hello-world vendor-chunk sizes [older]: Vue ~18.5 kB, Svelte 5 ~5.7 kB, React ~58 kB, Solid ~3.4 kB, Preact ~6.3 kB, Lit ~5.5 kB (compression not stated) — [gautemo/frontend-framework-size-analysis](https://github.com/gautemo/frontend-framework-size-analysis)
- Blog-level 2025/2026 figures: Svelte 5 minimal app ~2–5 kB gzipped; Solid core ~6–8 kB gzipped; React+ReactDOM ~42–45 kB gzipped (one outlier claims ~130 kB); Vue Vapor runtime 34 kB vs full VDOM ~46 kB; Preact "only 3kb" — [arc.dev Svelte vs Vue vs Solid](https://arc.dev/employer-blog/svelte-vs-vue-vs-solidjs/); [shouldiusethisframework React bundle](https://shouldiusethisframework.com/blog/react-bundle-size-problem); [prerender.io](https://prerender.io/blog/best-javascript-frameworks-pros-cons-and-statistics/)
- Expo SDK 56 supports web via react-dom or react-native-web, with Expo Router streaming SSR behind a flag (relevant only if RN is chosen) — [Expo SDK 56 changelog](https://expo.dev/changelog/sdk-56)

### Inferences
- If the shell is Capacitor and the UI is web, the framework choice is independent of the mobile decision. For KISS plus long-term maintainability: Lit + standard web components (no compiler step, platform-aligned, 5–6 kB) or Svelte 5 (compiler, smallest output, excellent DX) are the leanest. Solid has best-in-class satisfaction but a smaller hiring pool. Preact gives React API compatibility at ~3–6 kB and lets you reuse React-ecosystem a11y primitives via `preact/compat`, which is a pragmatic middle path.
- HTMX + server render is attractive for simplicity but weak for an offline-capable, biometric-gated mobile banking client where most interactions must work from local state; it fits better for the back-office/admin web.
- React 19 remains the lowest hiring risk and has the richest accessible-component ecosystem; its cost is ~40–55 kB gzipped runtime and more ecosystem churn. For a bank where accessibility compliance is a legal requirement (EAA), the a11y ecosystem argument is material.

### Gaps
- No 2025/2026 benchmark measuring all candidates with identical methodology and gzip; the 2024 repo is the only comparable dataset.
- State of JS 2025 per-framework usage/retention percentages were not present in the fetched page text (chart data rendered client-side); only qualitative rankings were captured.
- Hiring data (job-posting counts per framework) was not researched.

## Key Question 4: Free/open design-system and UI tooling; WCAG 2.2 and the European Accessibility Act

### Takeaway
Material Web (MWC) is in maintenance mode "pending new maintainers", so it is not a safe base. Radix/shadcn (React), Tailwind v4 and Open Props are free and active. The EAA has applied to consumer banking since 28 June 2025 with no grandfathering; EN 301 549 currently references WCAG 2.1 AA with a 2026 revision moving to WCAG 2.2 AA, so target WCAG 2.2 AA now, with special attention to Target Size and Accessible Authentication.

### Cited Findings
- Material Web README: "MWC is in maintenance mode pending new maintainers" (links discussion #5642); no release dates shown — [material-components/material-web](https://github.com/material-components/material-web)
- EAA applies to consumer banking services since 28 June 2025, including existing apps (no grandfathering) — [accessible.org EAA online banking](https://accessible.org/online-banking-accessibilityeaa/); [getwcag EAA guide](https://getwcag.com/en/what-is-european-accessibility-act-eaa)
- EN 301 549 currently points to WCAG 2.1 AA; a revision (v4, draft) moves to WCAG 2.2 AA and was expected to be cited in the EU Official Journal around October 2026 (secondary; sources disagree whether 2.2 is already referenced) — [isatis.com](https://isatis.com/blog/european-accessibility-act-build-requirement/); [accessscan EAA banking](https://accessscan.app/guides/eaa-compliance-for-banking)
- WCAG 2.2 criteria called out for banking UI: Target Size (2.5.8) and Accessible Authentication (3.3.8), which affects OTP entry and step-up flows — [yusmpgroup WCAG 2.2 2026](https://yusmpgroup.com/blog/web-app-accessibility-wcag-2026); [accessscan](https://accessscan.app/guides/eaa-compliance-for-banking)

### Inferences
- Avoid Material Web components as a foundation. If using Lit/web components, build a small in-house token + component set (Open Props for tokens is a lightweight, framework-agnostic choice) and lean on native HTML semantics; if using React/Preact, Radix primitives + shadcn copies give accessible headless behaviour without a dependency on a vendor's roadmap.
- WCAG 3.3.8 Accessible Authentication directly constrains login design: no cognitive-function tests (e.g., transcribing codes) without an alternative; passkeys/biometrics are the easiest compliant path, another reason a passkey-first login is desirable.

### Gaps
- Search budget ran out before verifying current status/licensing of Radix, shadcn, Tailwind v4 and Open Props from primary sources; these are widely known to be MIT-licensed OSS but that was not confirmed in this session.
- No source found comparing accessibility tooling (axe-core, Playwright a11y) across frameworks.

## Key Question 5: Secure client patterns (token storage, pinning, screenshot blocking, clipboard, secure enclave, attestation, anti-tampering)

### Takeaway
Hardware-backed keys (Keystore/Secure Enclave), Play Integrity + App Attest on the server, FLAG_SECURE on Android, token delivery into the WebView only after native authentication, and OWASP MASVS-RESILIENCE controls (root/jailbreak detection, attestation, integrity checks, obfuscation, debugger detection) form the baseline. iOS has no FLAG_SECURE equivalent. Attestation does not detect runtime hooking on its own.

### Cited Findings
- Android guidance: FLAG_SECURE "tells Android not to allow screenshots or to display the window view on a non-secure display (such as Casting the screen)" and is recommended for banking apps; it is per-window, so it must be set on the Activity hosting the WebView — [Android Developers: Secure sensitive activities](https://developer.android.com/security/fraud-prevention/activities)
- Play Integrity `appAccessRiskVerdict` detects apps that "could be used to capture the screen, display overlays, or control the device (for example, by misusing the accessibility permission)"; Google suggests challenging the user to disable such apps before high-value actions — [Play Integrity overview](https://developer.android.com/google/play/integrity/overview)
- App Attest: a genuine app on a jailbroken iPhone can pass App Attest, and Frida-style runtime hooking can still produce a valid assertion; attestation gives a strong device-integrity signal but "doesn't always catch runtime hooking" — [iPucu Lab App Attest and Play Integrity guide](https://ipucubilisim.com.tr/en/blog-app-attest-play-integrity.html)
- OWASP MASVS-RESILIENCE ("Resilience Against Reverse Engineering and Tampering") has controls RESILIENCE-1..4 with related weaknesses MASWE-0051..0065: root/jailbreak detection, emulator/virtual-device detection, device and app attestation, app and runtime integrity checks, code/resource obfuscation, debug-artifact removal, debugger and dynamic-analysis-tool detection — [OWASP MASVS-RESILIENCE-1](https://mas.owasp.org/MASVS/controls/MASVS-RESILIENCE-1/)
- WebView token delivery pattern (card-details use case): fresh token per load, strong auth before requesting the token, load only from a fixed HTTPS origin, deliver the token through the native bridge after the page signals ready, never before authentication — [BVNK: display card details in WebView](https://docs.bvnk.com/bvnk/use-cases/cards/display-card-details-webview/)
- Secure storage: tokens belong in Keychain/Keystore-backed storage, not SharedPreferences/AsyncStorage/localStorage (Flutter and RN examples) — [Medium Flutter banking security](https://medium.com/@sharmapraveen91/flutter-app-security-considerations-for-banking-applications-with-real-code-8aca5b595162); [NativePHP secure storage docs](https://nativephp.com/docs/mobile/2/apis/secure-storage)
- Capacitor OSS plugins for pinning, biometrics, Keystore/Keychain storage exist (see Q2); a post-quantum crypto plugin using Secure Enclave + Keystore (ML-DSA/ML-KEM) was announced on the Ionic forum — [Ionic forum PQC plugin](https://forum.ionicframework.com/t/post-quantum-crypto-plugin-for-capacitor-ml-dsa-ml-kem-secure-enclave-keystore/251695)
- Play Integrity "Caution": `requestHash`/`nonce` data is visible in cleartext to the app and Google; hash or encrypt before passing — [Play Integrity overview](https://developer.android.com/google/play/integrity/overview)
- Google-side root-hiding tooling ("Play Integrity Fix") exists and is actively maintained in 2026, i.e., `MEETS_BASIC_INTEGRITY` alone is bypassable — [shcho-i-yak blog (bypass tutorial, cited only as evidence that bypasses exist)](https://shcho-i-yak.pp.ua/en/posts/play-integrity-fix-root-hide-banking-apps/); [PrivSec banking-apps-compat-report issue #342](https://github.com/PrivSec-dev/banking-apps-compat-report/issues/342)

### Inferences
- In a Capacitor architecture: the native layer owns (a) a hardware-bound key pair (Secure Enclave / StrongBox Keystore) used to sign every sensitive request, satisfying EBA device binding; (b) Play Integrity / App Attest tokens attached to login and payment calls; (c) biometric gating via LocalAuthentication/BiometricPrompt with Keychain access control; (d) FLAG_SECURE on Android and a privacy overlay on iOS app-switcher snapshots; (e) certificate pinning in the native HTTP path. The web layer never holds long-lived secrets; it receives short-lived tokens via the bridge after native auth.
- Clipboard hygiene (clearing after N seconds, Android `ClipDescription.EXTRA_IS_SENSITIVE`) was not covered by any fetched source; treat as a gap to verify.
- Do not rely on `MEETS_BASIC_INTEGRITY`; enforce `MEETS_DEVICE_INTEGRITY` (and `MEETS_STRONG_INTEGRITY` for high-value actions where install base allows), plus server-side tiered responses, as Google recommends.

### Gaps
- Apple's App Attest page did not return content; exact rate limits and OS support are unsourced here.
- No source found on iOS screenshot prevention inside WKWebView; general knowledge is that iOS has no FLAG_SECURE equivalent, but this was not confirmed by a fetched Apple document.
- Clipboard-specific APIs and anti-tampering/obfuscation tooling for JS-in-WebView (vs native binaries) not researched.
- OWASP MAS profile/levels (L1/L2/R) text not retrieved (page body truncated).

## Key Question 6: Local-first and offline: what banks do about offline balances and queued payments; which sync engines are OSS and mature

### Takeaway
Banks do not do local-first money movement: a cached balance for display is the norm, and offline "payments" exist only in merchant-terminal SDKs with hard caps, 24-hour expiry and merchant-borne risk. For a client that needs offline read + queued intents, the OSS options are ElectricSQL (Apache-2.0, team now at Neon/Databricks; everything open-sourced stays open), Zero (Apache-2.0, needs zero-cache + Postgres), TinyBase (MIT, client-only store). PowerSync's server is source-available (FSL), and Replicache is commercial.

### Cited Findings
- Square offline payments: per-payment and total offline storage limits, payments "might be declined if not processed within 24 hours", seller bears risk of expired/declined/disputed offline payments; POS API returns a client-side ID instead of a transaction ID — [Square Mobile Payments SDK offline (Android)](https://developer.squareup.com/docs/mobile-payments-sdk/android/offline-payments); [Square POS API offline mode](https://developer.squareup.com/docs/pos-api/cookbook/offline-mode?q=sandbox)
- PayPal pauses offline payments after 24 hours without connection; SumUp provisionally approves offline on-device without real-time authorization — [PayPal offline payments](https://www.paypal.com/us/cshelp/article/what-are-offline-payments--help1311); [SumUp offline payments](https://developer.sumup.com/terminal-payments/offline-payments/)
- Offline-first banking architecture pattern: local DB first, per-record `sync_status`, sync on reconnect/app-resume/timer, queue + retry, explicit UI states (online / offline / syncing / queued N / retrying); "a product that caches a balance for display is not offline-first"; the hard question is reconciling a balance that goes negative offline — [mobibank.fi evaluating offline-first banking](https://www.mobibank.fi/how-to-evaluate-an-offline-first-banking-platform/); [dashdevs offline-first](https://dashdevs.com/blog/offline-applications-and-offline-first-design-challenges-and-solutions/); [purrweb banking UX](https://www.purrweb.com/blog/banking-app-design/)
- ElectricSQL: Apache-2.0; team announced Aug 11, 2026 it is joining Neon (owned by Databricks); "Everything the Electric team has open-sourced stays open source"; sync engine and PGlite coming to Neon platform; Electric Cloud's future is reported inconsistently (homepage still advertises it; one summary says shutting down) — [Electric: joining Databricks](https://electric.ax/blog/2026/08/11/electric-joining-databricks); [Neon blog: Electric joins Neon](https://neon.com/blog/electric-joins-neon); [Neon changelog Aug 14, 2026](https://neon.com/docs/changelog/2026-08-14); [Blocks & Files](https://www.blocksandfiles.com/ai-ml/2026/08/12/oh-no-not-another-one/5286721)
- Zero (Rocicorp mono): Apache-2.0; `packages/zero-cache` is the server component — [rocicorp/mono](https://github.com/rocicorp/mono); secondary: Zero 1.0 in June 2026, "less production-tested at scale" — [Kanopy Labs TanStack DB vs Electric vs Zero](https://kanopylabs.com/blog/tanstack-db-vs-electricsql-vs-zero-sync)
- PowerSync: client SDKs open source; sync service [SOURCE-AVAILABLE] under FSL-1.1-ALv2 — [PowerSync docs alternatives page](https://docs.powersync.com/resources/alternatives/neon-realtime.md)
- Replicache: commercial [PAID], free for non-commercial (secondary) — [RxDB alternatives](https://rxdb.info/alternatives.html)
- TinyBase: MIT, ~6.2 kB client store — [doolpa TinyBase review](https://doolpa.com/article/tinybase); [tinybase 7.3.4 on unpkg](https://app.unpkg.com/tinybase@7.3.4/files/agents.md)

### Inferences
- The bank client should be "offline-readable, online-transactional": cache accounts/transactions/cards in an encrypted local store (OPFS/IndexedDB in web; SQLite via Capacitor plugin in native), show last-synced timestamps, and queue only non-monetary intents (e.g., draft payee, category edits) or payment "drafts" that are explicitly submitted when online with fresh SCA. CRDT-grade conflict resolution is unnecessary and adds complexity; a per-record `sync_status` + server-authoritative ledger is the KISS design.
- Among sync engines, ElectricSQL (read-path sync from Postgres via shapes) is the best fit for "server-authoritative, client-cached" data; Zero adds write-path optimistic mutators if needed later. Both are Apache-2.0. PowerSync's FSL server is non-OSI, so it fails the "free OSS only" constraint for the server component.
- Electric's acquisition reduces vendor-lock risk for the OSS core (explicit commitment) but raises roadmap uncertainty for Electric Cloud; self-host.

### Gaps
- No public engineering source from any named bank describing its offline design; the pattern above is inferred from vendor and terminal-SDK docs.
- Zero's 1.0 date and Postgres requirement were not confirmed from the repo page (only secondary).
- CRDT libraries (Yjs, Automerge, Loro) were not researched; they are not needed for a ledger-centric client.

## Additional Area: How banks actually ship (2025–2026) and E2E testing

### Takeaway
