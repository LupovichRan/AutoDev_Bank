# Open-source core-banking and ledger engines (state as of early Nov 2026)

Scope note: all facts below were gathered on 2026-11-04 from project repos, docs and vendor pages. Items marked "(older)" are from 2023–2025 sources. The WebSearch budget for this session ran out mid-research; the remaining facts were pulled by direct fetches of primary pages, so a few items (notably the Midaz repository itself) could not be re-verified and are flagged in Gaps.

## KQ1. Comparative fact sheet of the viable options (license, maturity, language, store, consistency, throughput, multi-currency, idempotency, audit, maker-checker, API, footprint, community)

### Takeaway
Only four candidates are both truly OSS and purpose-built double-entry engines: TigerBeetle (Apache-2.0, Zig, its own replicated store), Formance Ledger (MIT, Go, now v3 on embedded Pebble+Raft), Blnk (Apache-2.0, Go, PostgreSQL+Redis) and the pgledger "starter kit" (MIT, pure PostgreSQL). Apache Fineract is the only full core-banking system (loans, savings, GL, maker-checker, COB batch) under Apache-2.0; Midaz has moved to the source-available Elastic License 2.0 and should be flagged; Open Bank Project is an AGPL/commercial API layer, not a ledger; Moov libs are Apache-2.0 payment-format libraries, not ledgers; plain-text tools (ledger-cli BSD, hledger GPL-3, beancount GPL-2) are personal/SMB accounting CLIs, not transactional engines.

### Cited Findings

**TigerBeetle**
- License Apache-2.0; 17.3k stars, 932 forks; described as "a financial transactions database built for mission-critical safety and performance"; CLI REPL; replica flags `--replica-count`/`--replica` — [GitHub](https://github.com/tigerbeetle/tigerbeetle)
- Latest releases: 0.17.9 (06 Jul 2026, reverts a unique-keys change, adds experimental `--memory` flag), 0.17.8 (22 Jun 2026, fixes a schema bug from 0.17.5 that could crash upgrades when pending transfers existed) — [Releases](https://github.com/tigerbeetle/tigerbeetle/releases)
- Timeline: 0.15.3 "released for production" March 2024; "production customers hit 100M transactions per month" January 2025; "processed a trillion transactions to test TigerBeetle's scale" 19 March 2026 — [tigerbeetle.com/company](https://www.tigerbeetle.com/company)
- Consistency: Viewstamped Replication; "Only strict serializability is offered"; transfers run one at a time on a single core; each transfer has a unique client-generated u128 ID and "is processed at most once, even when clients retry"; recommends six replicas across three cloud providers (two per provider) with flexible quorums; storage: immutable, checksummed, hash-chained data with Protocol-Aware Recovery; VOPR simulator runs 24/7 on 1024 cores; each op stored in a quorum of WALs before ack — [Safety docs](https://docs.tigerbeetle.com/concepts/safety/)
- Jepsen (Kyle Kingsbury, 2025-06-06, funded by TigerBeetle) tested 0.16.11–0.16.30: "appeared to meet its promise of Strong Serializability" as of 0.16.30; found 2 safety issues (query filter omissions #2544 fixed 0.16.17; Java client timestamp bug #2495 fixed 0.16.14) and 7 crashes; unresolved: requests never time out (#206); recommends ≥0.16.43; "exceptional resilience to disk corruption" — [Jepsen](https://jepsen.io/analyses/tigerbeetle-0.16.11)
- Data model: amounts are unsigned 128-bit integers; `ledger` (u32) partitions accounts by currency/asset and only same-ledger accounts transact; accounts and transfers are immutable (changing asset scale means a new ledger); `id` is the idempotency key, unique per cluster; recommended ID = 48-bit ms timestamp + 80 random bits; `user_data_128/64/32` and `code` (u16) for linking to a control-plane DB — [Data modeling](https://docs.tigerbeetle.com/coding/data-modeling/)
- Transfer flags: `linked`, `pending`, `post_pending_transfer`, `void_pending_transfer`, `balancing_debit/credit`, `closing_debit/credit` (require pending), `imported` (user-supplied historical timestamp, strictly increasing, no timeout); `timeout` seconds on pending transfers; "Transfers cannot be modified or deleted after creation"; a pending transfer can be resolved at most once; timestamps are 64-bit ns set by the cluster — [Transfer reference](https://docs.tigerbeetle.com/reference/transfer/)
- Account balance limits via `flags.credits_must_not_exceed_debits` / `flags.debits_must_not_exceed_credits`; balances computed by the app as debits−credits or credits−debits — [Data modeling](https://docs.tigerbeetle.com/coding/data-modeling/)
- Performance design: batches up to 8,190 transfers per request; single-threaded state machine ("Adding nodes improves reliability but not throughput"); static allocation, 128-byte cache-aligned transfers, io_uring; no published throughput number on this page — [Performance](https://docs.tigerbeetle.com/concepts/performance/)
- Maintainers state the database is intentionally not horizontally scalable and transactions are processed by a single core (older, GitHub issue) — [Issue #1940](https://github.com/tigerbeetle/tigerbeetle/issues/1940)
- Trillion-transactions test (Mar 2026): cluster on local NVMe plus object storage holding half a petabyte of flash; "diagonal scaling" tiers older LSM levels to object storage; no throughput/duration numbers in the post (deferred to a video) — [Blog](https://www.tigerbeetle.com/blog/2026-03-19-a-trillion-transactions)
- Hardware: 1 core per replica (+1 for OS); ECC RAM required in production, min 6 GiB, 16–32+ GiB recommended; local NVMe recommended, ~16 TiB for 40 billion transfers; ext4 caps at 16 TiB; ≥1 Gbps network; remote block storage works but slower — [Hardware](https://docs.tigerbeetle.com/operating/hardware/)
- Deployment: single statically linked binary; each replica on its own machine; production example uses six replicas; cluster size cannot be changed after creation; needs a supervisor to restart replicas — [Deploying](https://docs.tigerbeetle.com/operating/deploying/)
- Recommended architecture: TigerBeetle is the OLTP "data plane"; a general-purpose DB (e.g., Postgres) is the "control plane" for names/metadata; "initiating a transfer should not require fetching metadata from the general purpose database"; TigerBeetle has no authentication and must never be exposed to untrusted clients — [System architecture](https://docs.tigerbeetle.com/coding/system-architecture/)
- Multi-currency: one ledger per currency; FX is two (or three, with spread) linked transfers through per-currency liquidity accounts; rate is implicit in amounts; round in the liquidity provider's favour — [Currency exchange recipe](https://docs.tigerbeetle.com/coding/recipes/currency-exchange/)
- No maker-checker, no API gateway, no auth: the model is "two entities (accounts and transfers) and one invariant" — [Debit/credit concept](https://docs.tigerbeetle.com/concepts/debit-credit/)
- Company: spun out as a startup after customer requests for enterprise support; "paying customers since day one"; $24M Series A (2024) — [TechCrunch](https://techcrunch.com/2024/07/23/tigerbeetle-is-building-database-software-optimized-for-financial-transactions); [FinTech Futures](https://www.fintechfutures.com/data-privacy-security/financial-transactions-database-tigerbeetle-raises-24m-series-a-funding)
- Thoughtworks Technology Radar listed TigerBeetle (Apr 2024, older) — [Thoughtworks](https://thoughtworks.com/radar/platforms/tigerbeetle)

**Formance Ledger**
- GitHub repo now describes "Ledger v3 (Raft Cluster)": storage is Pebble (CockroachDB's LSM engine, pure Go), consensus etcd/raft with a single Raft group for all ledgers; "Built-in idempotency key support for safe retries"; Numscript; bulk ops; Ed25519 request signing; HTTP :9000 + gRPC :8888; Go 1.27+, Just, Nix required for quick start; 1.5k stars, 224 forks; no LICENSE file visible in the file listing — [GitHub](https://github.com/formancehq/ledger)
- Sales/overview doc: v2 depended on PostgreSQL ("required a managed database, connection pooling, replication setup, and a DBA"), v3 removes PostgreSQL for in-process Pebble; v3 = 3-node Raft, writes acknowledged after majority replication; backups are a directory copy; benchmark 106,000 tx/s sustained, p99 < 75 ms at full load on 3 nodes × 8 cores × 4 GiB; "append-only balance diffs to avoid lock contention on hot accounts"; global audit log ordered by Raft; event sinks Kafka/NATS/ClickHouse/Databricks — [docs/sales](https://github.com/formancehq/ledger/blob/main/docs/sales)
- Pricing page: Open Source tier "MIT License", includes double-entry core ledger, Numscript DSL, multi-currency and multi-asset tracking, Generic Connector, CLI/SDKs, full source; Enterprise (annual subscription) adds PSP/bank connectors, Wallets/Flows/Reconciliation modules, Enterprise Auth/Auditing/Observability/Streaming, Web Console, managed deployment, 24/7 support — [Formance pricing](https://www.formance.com/pricing)
- $21M Series A (2023, older) co-led by PayPal Ventures and Portage — [PYMNTS](https://www.pymnts.com/?p=2435273)
- Older v2 README (mirror/fork) described: "programmable financial core ledger", "atomic multi-postings transactions system", programmable in Numscript, MIT — [search snippet via GitHub topics](https://github.com/formancehq)

**Blnk**
- "open-source, double-entry ledger for teams building fintech products"; "This project uses the Apache License 2.0"; use cases wallets, lending, loyalty, escrow; Discord; paid support plans — [README](https://raw.githubusercontent.com/blnkfinance/blnk/main/README.md)
- Required stores: PostgreSQL (only supported DB) and Redis (queues, distributed balance locks, webhook queues, worker coordination); Typesense optional for search; release line 0.15.x (0.15.4/0.15.5 referenced) — [Data stores](https://docs.blnkfinance.com/operating/configuration/data-stores.md)
- Concurrency: transactions saved as QUEUED and sharded by hash of source balance across `BLNK_QUEUE_NUMBER_OF_QUEUES` (default 20) workers; Redis locks acquired on involved balances "in a consistent order to prevent deadlocks"; optimistic `version` on balances as "the database-level safety net"; `skip_queue=true` for synchronous processing — [Concurrency](https://docs.blnkfinance.com/guides/concurrency.md)
- Precision: amounts stored as integers in minor units (`precise_amount` + `precision`, e.g., USD 750.23 → 75023 / 100; BTC uses 1e8); negatives rejected — [Precision](https://docs.blnkfinance.com/transactions/precision.md)
- Inflight (hold) transactions: `inflight: true` reserves on `inflight_debit_balance/inflight_credit_balance`; commit (full or partial, multiple commits allowed up to original hold), void releases remainder; available since 0.6.0, bulk inflight since 0.9.0 — [Create inflight](https://docs.blnkfinance.com/transactions/inflight); [Commit](https://docs.blnkfinance.com/transactions/inflight/commit-inflight.md)
- Tamper-evidence: always-on SHA-256 per-transaction hash over amount/reference/currency/source/destination; optional global hash chain (Core 0.15.0+), verified via `blnk verify-chain`, DB trigger guards protected fields — [Hash](https://docs.blnkfinance.com/transactions/hash.md)
- Enterprise Core (license key `ENTERPRISE_LICENSE_B64`, container exits if invalid) adds RBAC, SQL data lake, alerts, audit logs, MCP/agents, dashboard; open-source Core is deployed first and Enterprise runs beside it — [Enterprise](https://docs.blnkfinance.com/deploy/enterprise.md)
- Self-host via `docker compose up` at :5001; SDKs for TypeScript, Go, Python, Java + CLI; `allow_overdraft` flag; `reference` field per transaction — [Install](https://docs.blnkfinance.com/home/install)
- Balance monitors and reconciliation modules exist in docs — [llms.txt index](https://docs.blnkfinance.com/llms.txt)

### Inferences
- For a greenfield 2026 digital bank on free infra, the realistic shortlist is: TigerBeetle (ledger kernel) + Postgres control plane; Formance Ledger v3 (self-contained Raft cluster, MIT, but operationally newer than v2 and no longer Postgres-backed); Blnk (Postgres+Redis, simplest ops, but relies on Redis locks + optimistic versioning rather than DB-enforced invariants); or an in-house Postgres ledger seeded from pgledger. Fineract is the only option that also ships product logic (loans, savings, interest, accruals, COB, maker-checker, multi-tenancy) but it is a large Java monolith with "no comprehensive production deployment guide."
- Midaz must be excluded or treated as a license risk: ELv2 forbids offering it as a hosted service and relies on license-key gating, and the Apache→ELv2 change happened after v1.2.0.
- Formance's v3 move from PostgreSQL to embedded Pebble+Raft (requiring Go 1.27, Just, Nix for dev) means an adopter inherits a new consensus/storage stack; the 106k tx/s benchmark is vendor-published and not independently verified.
- Fineract's "four-eyes" maker-checker is the only turnkey maker-checker found among OSS options; TigerBeetle, Formance, Blnk and pgledger leave maker-checker to the application layer.

## KQ3. Essential invariants and design patterns of a correct double-entry ledger, and which options support them

### Takeaway
The consensus pattern set across TigerBeetle, Square Books, Modern Treasury, Fowler and pgledger is: append-only immutable journal; every transaction balances to zero (per currency); integer minor-unit amounts; client-supplied idempotency keys; two-phase (pending→posted/voided) transfers with timeouts; derived or versioned running balances; corrections by reversal not edit; period close/locking; and a separate control plane for mutable business metadata.

### Cited Findings

**Invariants / patterns (reference sources)**
- Fowler: an Account's balance "is derived as the sum of all the Accounting Entrys"; Accounting Transaction links the entries of one transfer; Reversal Adjustment leaves incorrect transactions in place and posts opposite entries; Posting Rules map Domain Events to Accounting Transactions (event sourcing) — [Fowler, Accounting Narrative](https://www.martinfowler.com/eaaDev/AccountingNarrative.html); book chapter "Inventory and Accounting" covers Account, Transactions, Summary/Memo Account, Posting Rules — [Analysis Patterns ch.6](https://martinfowler.com/apsupp/apchap6.pdf)
- Square Books: every change is a journal entry that must balance to zero; three tables `books`, `journal_entries`, `book_entries`; journal/book entries append-only, only `books.balance` mutable, with per-book version counter; corrections by new entries ("this is a feature"); debits positive/credits negative sign convention took practice to internalise; UUIDs and interleaved tables to avoid Spanner hotspots — [Square blog](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)
- Modern Treasury: "mutable while pending and immutable once posted"; corrections via reversal entry or difference entry; business objects (Orders) are a mutable presentation layer, ledger transactions are the source of truth; one order ↔ many ledger transactions — [MT immutability](https://www.moderntreasury.com/journal/enforcing-immutability-in-your-double-entry-ledger)
- Modern Treasury balances: Posted (posted only), Pending (posted + pending), Available ("assuming outgoing funds are gone and incoming funds haven't arrived" — "the safest approach to take when approving a transaction") — [MT balances](https://www.moderntreasury.com/journal/how-to-think-about-ledger-balances); account balances derived from five fields (posted/pending debits & credits + normal balance), entries immutable apart from `discarded_at` on pending entries — [MT scale part II](https://www.moderntreasury.com/journal/how-to-scale-a-ledger-part-ii)
- pgrs.net: ledger = current balance + immutable history + source of each change; transfers' rows sum to zero; "No creation from nothing"; atomicity; append-only history as audit trail; critiques `UPDATE users SET points = points + 100` — [pgrs.net](https://www.pgrs.net/2025/06/17/double-entry-ledgers-missing-primitive-in-modern-software/)
- HN thread on that post: practitioners stress historical balances (balance-at-time), running balance per entry vs periodic checkpoints/closed periods, and GianFabien: "The surprising thing is that no two were the same" (multi-currency spot/forward FX was the hardest case) — [HN 44320050](https://news.ycombinator.com/item?id=44320050)
- TigerBeetle: "two entities (accounts and transfers) and one invariant (every debit has an equal and opposite credit)"; recorded transfers cannot be erased — [Debit/credit](https://docs.tigerbeetle.com/concepts/debit-credit/)
- dev.to (Almeida): push invariants into Postgres with deferred triggers checking debits=credits per currency at commit; unique constraint for idempotency so one insert wins — [dev.to](https://dev.to/tomasralmeida/why-building-a-ledger-is-harder-than-it-looks-21cm)

**Support matrix (from the cited docs above)**
- Immutable journal: TigerBeetle yes (DB-enforced); Formance v3 "global audit log ordered by Raft"; Blnk per-row SHA-256 + optional hash chain + DB trigger; pgledger append-only entries (convention, SQL functions); Fineract journal entries with reversal + period close locks; Square/MT yes.
- Balanced postings: TigerBeetle each transfer = one debit + one credit (compound via linked transfers); Formance multi-posting transactions via Numscript; Blnk source→destination with splits; pgledger two entries per transfer, batch all-or-nothing; ledger-core deferrable constraint trigger.
- Idempotency keys: TigerBeetle `id` (u128, at-most-once); Formance built-in idempotency key; pgledger `idempotency_key` (Oct 2026); Blnk `reference` (behaviour on retry not documented); Fineract — not found; MT `external_id` (behaviour not confirmed).
- Two-phase pending/posted + holds + timeouts: TigerBeetle `pending`/`post`/`void` with `timeout` and partial post; Blnk inflight with partial/multiple commits and void; MT pending/posted/archived; Formance — holds not documented in v3 pages fetched (Numscript overdraft control exists); pgledger — none (would be modelled with holding accounts).
- Balance bounds/overdraft control: TigerBeetle account flags; Blnk `allow_overdraft`; pgledger `allow_negative_balance`; Formance Numscript overdraft control.
- Multi-currency: TigerBeetle ledger-per-currency + linked FX transfers; Formance multi-asset; Blnk per-transaction `currency` + precision; pgledger currency per account; Fineract organisation currency list.
- Interest accrual / EOD batching: Fineract only (accrual jobs, scheduler jobs, COB Spring Batch, closing entries). TigerBeetle/Formance/Blnk/pgledger have no interest or EOD logic; TigerBeetle's `imported` flag supports loading historical/batched events with user timestamps.
- Maker-checker: Fineract only.
- Balance-at-time: pgledger stores previous/current balance per entry; Blnk "balance snapshots and historical balances"; TigerBeetle exposes cumulative debits/credits (history via `get_account_transfers`/balances recipes); Fineract via journal search.

### Inferences
- A minimal correct bank ledger must implement at least: integer minor units, balanced-by-currency transactions enforced at commit, append-only entries with reversal-only corrections, idempotency key uniqueness, pending/posted/voided state with expiry, per-account balance bounds, and a period-close lock. Only TigerBeetle enforces nearly all of these inside the database; Blnk/Formance enforce them in the service; pgledger enforces them in SQL functions; Fineract adds the banking-product layer on top.

### Gaps
- No source fetched describes Formance v3's hold/pending semantics; v2 docs could not be fetched (docs.formance.com returned empty bodies).
- No authoritative source found for timezone handling patterns (see KQ5).

## KQ4. In-house minimal ledger on PostgreSQL vs adopting TigerBeetle: complexity and reference designs

### Takeaway
A minimal correct Postgres ledger is small (pgledger is one SQL file: accounts, transfers, entries, a few functions) and reaches ~10k transfers/s on a laptop, but the hard parts are idempotency under concurrency, hot-account locking, historical balances and operational discipline; TigerBeetle removes those classes of bugs (strict serializability, at-most-once IDs, DB-enforced balances, two-phase transfers) at the cost of a new Zig binary cluster (6 replicas recommended, dedicated machines, ECC/NVMe), a mandatory separate control-plane DB, no auth, and no SQL/joins.

### Cited Findings
- pgledger: "The ledger implementation is currently in a single file: pgledger.sql"; tables/views for accounts (balance, version), transfers (from/to, amount, event_at, metadata, idempotency_key), entries (previous/current balance, version) — [GitHub](https://github.com/pgr0ss/pgledger); [srclog](https://srclog.com/pgledger)
- pgledger concurrency: concurrent duplicate idempotent calls wait and return the same result under Read Committed but fail under Repeatable Read/Serializable and must be retried; Go test suite includes deadlock/race tests; author: "building a ledger properly from scratch is tricky, and there are lots of potential edge cases and race conditions" — [GitHub](https://github.com/pgr0ss/pgledger); [pgrs.net Mar 2025](https://pgrs.net/2025/03/24/pgledger-ledger-implementation-in-postgresql/)
- pgledger throughput: 10,637 tx/s on M3 MacBook Air with vanilla Postgres 17.5; −29% when accounts drop from 50 to 10 (hot accounts); 1,631 tx/s on Neon free tier due to network latency; "expects other database bottlenecks to appear before pgledger's limits do" — [pgrs.net May 2025](https://www.pgrs.net/2025/05/16/pgledger-in-postgresql-is-fast/)
- pgledger author now frames it as "a starter kit for a ledger" to copy and adapt, and only adds features that are "widely requested, complicated, or built into core functions" (idempotency was "tricky to implement correctly") — [pgrs.net Oct 2026](https://www.pgrs.net/2026/10/29/coding-agents-starter-kits-and-pgledger/)
- ledger-core: debits=credits enforced by a deferrable constraint trigger in PostgreSQL 18 — [GitHub](https://github.com/ByteEntropyDotCom/ledger-core)
- Almeida (dev.to): deferred triggers checking per-currency balance at commit; unique constraint for duplicates — [dev.to](https://dev.to/tomasralmeida/why-building-a-ledger-is-harder-than-it-looks-21cm)
- HackerNoon: read-then-update (SELECT, check, UPDATE) leaves a race window; make check+write atomic in the DB; store amounts as 64-bit integers in smallest unit — [HackerNoon](https://hackernoon.com/designing-a-concurrent-donation-ledger-with-fastapi-and-postgresql)
- Square Books: balances stored and updated per operation (not recomputed), version counter per book; schema designed to avoid Spanner hotspots (UUIDs, interleaving) — [Square](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)
- Modern Treasury: five stored balance fields per account, compute balances "upon request"; entries immutable except `discarded_at` for pending — [MT](https://www.moderntreasury.com/journal/how-to-scale-a-ledger-part-ii)
- TigerBeetle complexity/ops: dedicated machine per replica; 6 replicas in production example; cluster size fixed at creation; single static binary; needs supervisor — [Deploying](https://docs.tigerbeetle.com/operating/deploying/); ECC RAM required, NVMe recommended — [Hardware](https://docs.tigerbeetle.com/operating/hardware/); must pair with a general-purpose control-plane DB and must never be exposed to untrusted clients (no auth) — [System architecture](https://docs.tigerbeetle.com/coding/system-architecture/)
- TigerBeetle guarantees that an in-house ledger must otherwise build: strict serializability, at-most-once by u128 id, VSR replication, hash-chained checksummed storage, 24/7 simulation testing — [Safety](https://docs.tigerbeetle.com/concepts/safety/); two-phase transfers with expiry and single resolution — [Transfer reference](https://docs.tigerbeetle.com/reference/transfer/)
- TigerBeetle constraints: single core/leader processes all events, not horizontally scalable — [Performance](https://docs.tigerbeetle.com/concepts/performance/); [Issue #1940](https://github.com/tigerbeetle/tigerbeetle/issues/1940); Jepsen: client requests never time out (#206 unresolved) and several upgrade-path crashes in 0.16.x — [Jepsen](https://jepsen.io/analyses/tigerbeetle-0.16.11); 0.17.8 fixed an upgrade crash when pending transfers existed — [Releases](https://github.com/tigerbeetle/tigerbeetle/releases)
- TigerBeetle argues horizontally sharded clusters can be slower than single-node Postgres for OLTP under contention (no figures) — [Trillion blog](https://www.tigerbeetle.com/blog/2026-03-19-a-trillion-transactions)
- Super Payments chose TigerBeetle specifically because hot shared accounts caused row-lock bottlenecks in their prior relational design — [TigerBeetle story](https://tigerbeetle.com/stories/super)
- Older HN sentiment (2023–24): "if you are building a financial ledger I would way rather be interfacing with TigerBeetle than building up an application-driven ledger in Postgres" — [SaaSHub HN digest](https://www.saashub.com/tigerbeetle)
- Modern Treasury notes that Square, Uber and others wrote about building in-house ledger infrastructure — [MT Ledgers announcement](https://www.moderntreasury.com/journal/announcing-ledgers)

### Inferences
- Complexity estimate for in-house Postgres ledger (from pgledger/ledger-core/Almeida designs): 3 tables (accounts with currency+version+balance, transactions with idempotency_key UNIQUE, entries with signed/directional amount + running balance), 1 deferrable constraint trigger (sum per transaction per currency = 0), `SELECT ... FOR UPDATE` on accounts in sorted ID order, NUMERIC or BIGINT minor units, and a holds/pending modelled as either status columns or dedicated pending accounts. That is a few hundred lines of SQL — the risk is not size but subtle concurrency/retry semantics, which pgledger's author calls "tricky."
- At a new digital bank's volumes (Super Payments metadata shows ~100 TPS), Postgres throughput is not the constraint; the trade is "own every invariant in SQL + app" vs "operate a 6-node Zig cluster plus a control-plane DB and lose SQL queryability for financial rows."
- A pragmatic hybrid used by TigerBeetle's own architecture guidance: Postgres as system-of-record for customers/products/metadata; TigerBeetle (or an in-house ledger table set) strictly for balances and transfers.

### Gaps
- No independent benchmark comparing TigerBeetle vs a tuned Postgres ledger at identical workloads was found; the "1,000x" figure appears only on third-party marketing pages (e.g., banq.ai) and is unverified.
- The Slope "five most common pitfalls" post (Nov 2023) could not be fetched (403); only the snippet "immutable, insert-only design" was available — [Medium](https://medium.com/slope-stories/solving-the-five-most-common-pitfalls-from-building-a-payments-ledger-0afe1a6eceae)

## KQ5. Known pitfalls (floating point, timezone, currency minor units, race conditions, double-spend)

### Takeaway
Every credible source converges on: never use floats (use integer minor units or NUMERIC), make the balance check and write atomic (row locks in consistent order or a single-threaded state machine), enforce idempotency at the storage layer, model holds explicitly (pending/inflight) to prevent double-spend, record both system time and business/effective time, and lock closed periods; timezone handling is under-documented in the sources found.

### Cited Findings
- Floating point: Tom Lane on a float4 ledger mismatch — exact results call for "an exact datatype, ie numeric"; float4 "only has about six significant digits at best" (older) — [PostgreSQL list](https://postgrespro.com/list/thread-id/1207554)
- TigerBeetle: amounts are u128 integers; "map the smallest useful unit of the fractional currency to 1"; choose asset scale carefully because changing it requires a new ledger — [Data modeling](https://docs.tigerbeetle.com/coding/data-modeling/)
- Blnk: integers in minor units with per-currency `precision` (USD 100, BTC 1e8); "keep the same precision for every transaction in a given currency" — [Precision](https://docs.blnkfinance.com/transactions/precision.md)
- HackerNoon: 64-bit integers in smallest currency unit to avoid drift — [HackerNoon](https://hackernoon.com/designing-a-concurrent-donation-ledger-with-fastapi-and-postgresql); dev.to: BIGINT cents — [dev.to (Nosatov)](https://dev.to/igornosatov_15/-the-23-million-lesson-why-your-postgresql-money-transactions-are-probably-wrong-15l1)
- FX rounding: with an imprecise rate, "the application rounds in the liquidity account's favor"; record spread as a separate transfer so rate and spread remain recoverable — [TigerBeetle FX recipe](https://docs.tigerbeetle.com/coding/recipes/currency-exchange/)
- Race conditions / double-spend: SELECT-check-UPDATE race window; fix by atomic check+write in DB — [HackerNoon](https://hackernoon.com/designing-a-concurrent-donation-ledger-with-fastapi-and-postgresql); Blnk acquires balance locks "in a consistent order to prevent deadlocks" plus optimistic version check — [Blnk concurrency](https://docs.blnkfinance.com/guides/concurrency.md); TigerBeetle processes transfers one at a time on a single core with strict serializability — [Safety](https://docs.tigerbeetle.com/concepts/safety/); pgledger shows hot-account contention costing ~29% throughput — [pgrs.net](https://www.pgrs.net/2025/05/16/pgledger-in-postgresql-is-fast/)
- Idempotency pitfalls: pgledger — reuse of key with different arguments must error; concurrent duplicates behave differently under Read Committed vs Serializable — [GitHub](https://github.com/pgr0ss/pgledger); TigerBeetle — avoid central ID generators and purely random IDs (monotonic IDs give better throughput); IDs unique per cluster not per ledger — [Data modeling](https://docs.tigerbeetle.com/coding/data-modeling/); Jepsen — TigerBeetle clients retry indefinitely, turning definite errors into indefinite ones — [Jepsen](https://jepsen.io/analyses/tigerbeetle-0.16.11)
- Holds / authorisation double-spend: pending transfers reserve in `debits_pending/credits_pending` and expire exactly at timestamp+timeout; expired transfers cannot be posted or voided; removal of expired pending balances is best-effort so balances "may still appear pending briefly after expiry" — [Transfer reference](https://docs.tigerbeetle.com/reference/transfer/); Blnk multiple partial commits cannot exceed the original hold (`TXN_COMMIT_AMOUNT_EXCEEDED`) — [Commit inflight](https://docs.blnkfinance.com/transactions/inflight/commit-inflight.md); Modern Treasury: use Available balance (assume outgoing gone, incoming not arrived) when approving — [MT balances](https://www.moderntreasury.com/journal/how-to-think-about-ledger-balances)
- Time: TigerBeetle sets system timestamps itself (cluster time, no reliance on synced clocks) and suggests `user_data_64` for real-world "when" (bitemporality); `imported` events must have strictly increasing, non-future timestamps — [Data modeling](https://docs.tigerbeetle.com/coding/data-modeling/); [Transfer reference](https://docs.tigerbeetle.com/reference/transfer/); pgledger separates `created_at` from `event_at` for backdating — [GitHub](https://github.com/pgr0ss/pgledger); Fineract blocks transactions dated before a closure and requires deleting the closure to backdate — [Mifos closing entries](https://docs.mifos.org/mifosx/user-manual/for-operational-users-mifos-x-web-app/accounting-operations/closing-entries.md)
- Immutability pitfalls: Square — only `books.balance` is mutable; mistakes fixed with correcting entries — [Square](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/); Blnk hash excludes `description`, `status`, `meta_data` from the per-row hash (so those remain mutable) — [Blnk hash](https://docs.blnkfinance.com/transactions/hash.md)
- Sign conventions are a human-error source: Square's team "needed exercises and practice" for debit-positive/credit-negative — [Square](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)
- Upgrade/ops pitfalls (TigerBeetle): checkpoint divergence on upgrade 0.16.25→0.16.26 during state sync documented but not patched; `tigerbeetle recover` added in 0.16.43 for disk-loss recovery — [Jepsen](https://jepsen.io/analyses/tigerbeetle-0.16.11)

### Inferences
- The two pitfalls most likely to bite an in-house Postgres ledger are (a) idempotency semantics under concurrent retries (isolation-level dependent, as pgledger documents) and (b) hot shared accounts (fees, settlement, treasury) serialising on row locks — both are exactly the problems Super Payments cited when moving to TigerBeetle.
- Store two timestamps per entry (system/commit time and effective/value date in UTC) and treat "business day"/EOD as an application concept keyed to the bank's local calendar; close periods explicitly rather than relying on wall-clock boundaries.

### Gaps
- No authoritative 2024–2026 source specifically on timezone/value-date pitfalls in ledgers was found before the search budget was exhausted; the above is inferred from TigerBeetle's bitemporal guidance, pgledger's `event_at`, and Fineract's closing-entries behaviour.
- The Slope "five pitfalls" article (likely covering idempotency, precision, timezones, concurrency, reconciliation) could not be fetched.
